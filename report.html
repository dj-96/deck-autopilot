2. Motivation

Who has the problem. Junior consultants and analysts who own recurring decks: the monthly business review for a client, the weekly steering-committee update, the KPI pack for a portfolio company. In strategy consulting this work lands on the most junior person on the team, every cycle, and it was one of my frustrations in my own consulting job: the information is general and recurring, yet turning new data into slides took the same manual effort every cycle.

How it's done today. Export the new month's data, recompute the comparisons in Excel, paste them into the chart tool, rewrite every action title whose story changed, then re-check every number, because a single wrong figure in front of a client costs more credibility than the whole deck earns. Teams use think-cell or UpSlide to keep charts linked to Excel, but nothing writes the narrative and nothing checks the text.

What it costs. I assume a 7–8 slide recurring refresh takes about 3 hours of a junior consultant's time including checks, about 10 such refreshes a month per consultant, and a loaded cost of about $100/hour. These are estimates, not measurements (section 7 shows how the conclusions change if they are wrong). On those assumptions one consultant spends about 30 hours, or $3,000, a month on low-learning work, and the error risk never goes away.

Why anyone should care. Firms pay senior rates for judgment and junior rates for assembly. Making the recurring "keep it updated" phase nearly free also changes what consultants can offer: one of my frustrations was that engagements ended at strategic advice, with no ongoing operational support. If refreshing the client's numbers costs cents and minutes, ongoing reporting becomes something a team can afford to keep doing after the main project ends.

The closest alternative is pasting the data into ChatGPT, so I measured it. Same model, both CSVs pasted into one prompt, asked for the same deck, 5 times. I then checked every number it wrote against 2,565 exactly computed facts and recomputed by hand the ones that didn't match. Result: 265 of 266 numbers were correct and 1 was wrong ("Accessories added $18,988"; the truth is $8,988), so 1 in 5 decks contained a wrong number, and nothing in the output says which one. So the honest case is not that a single prompt is usually wrong; on 64 rows it is usually right. The case is that you can't tell which number is wrong, so someone still has to check all ~55 of them by hand. Deck Autopilot does that check, shows the source of every number (Figure 4), and its cost does not grow with every pasted row (section 5).

What is different, in one line: the model chooses what matters and writes it; code computes every number and proves every sentence.

4. The agents

StepTypeWhat it doesTools / output
GuardPythonReads both files; enforces 2 MB / 5,000 rows / .csv or .xlsx; checks both periods share columns; sorts columns into metrics, dimensions, and notes; quarantines any text cell that reads like an instruction to an AIClean data + safety log
Analyst agentLLMDecides which comparisons matter and drills into what drove each change; never does arithmeticget_schema, compare_total, compare_by (1–3 dimensions, sorted by biggest mover), compare_ratio (e.g. return rate), define_metric (e.g. gross profit), read_notes (untrusted text), submit_findings (must cite real fact IDs). Every computed number becomes a fact: ID, value, label, formula
Storyliner agentLLMTurns findings into a pyramid-principle deck: executive summary, 4–6 slides with action titles, bullets, chart specs, speaker notesStructured output (Pydantic schema). Bullets and titles cite fact IDs; charts contain only fact IDs, so the renderer looks values up and a chart can't show an invented number
Fact-checkerPythonExtracts every number from every title and bullet and matches it to the cited facts at the precision written ($64K matches $64,110; $70K doesn't); adds missing citations; sends violations backUp to 2 fix rounds; anything still wrong is flagged red on the slide
RendererPythonBuilds the web preview and an editable .pptx with native PowerPoint charts; speaker notes list the facts behind each slideDownload

Why organized this way. A fixed pipeline with one feedback loop, rather than agents chatting freely, keeps cost predictable (6–8 model calls a run) and makes each step testable on its own. The model is used only where judgment is needed (what matters, how to say it) and code is used wherever correctness is needed (math, checking, rendering). Two agents instead of one keeps each prompt short and focused: the Analyst never sees slide-writing instructions, and the Storyliner never sees raw data, only facts.

Model. Both agents use gpt-6-luna, the only model allowed on the course key, and an inexpensive one ($0.10 / $0.50 per million input / output tokens). Because math lives in tools, the model's job is selection and writing, which a small model does well: 10/10 clean runs passed the fact-check on the first draft. The app tries the course Portkey key first and falls back automatically to an OpenAI key with the same model; Portkey was out of budget during testing, so every run in this report went through the fallback.

What I did to keep cost down

  • Math in Python, not in the prompt. The model sees compact aggregates from tools, never the raw rows. A single prompt with the CSVs pasted is cheaper on this tiny sample ($0.0020 vs $0.0041) but grows by about 43 tokens per row: roughly 42,656 input tokens at 500 rows per file and 426,562 at 5,000 (extrapolated). The pipeline's input is bounded by its tool caps instead (not yet measured on large files).
  • Prompt caching. Instructions and tool schemas come first and never change, so repeated calls hit the cache: 53% of input tokens were cached, saving 23% ($0.0054 without caching). Caching changes cost, not output.
  • Parallel tool calls. The Analyst issues several tool calls per turn, so ~22 tool calls take only ~5–6 model turns, and each turn re-sends the growing context only once.
  • Caps that bound context. At most 25 groups per breakdown and a cap on facts per run (200 in these runs, now 400; see below), so the Storyliner's input stays small (about 7K tokens at 200).

Did cost cutting hurt performance? The 200-fact cap is the lever that bites: it fired in 9 of 10 clean runs. The quality measure is whether the deck found the three stories planted in the sample data: the Northeast online Camping promotion (10/10), the West store decline (10/10), and rising Footwear returns (8/10), the one the cap could plausibly cut off.

Did the cap hurt quality? A controlled test. I re-ran 6 clean runs with the cap doubled to 400 facts. Yes, it did: with the cap at 400, every run found all three stories, and no run hit the cap, for $0.0003 more per deck (+7%). So I changed the app: the default cap is now 400. This is a cost cut I reversed because the evidence said it was hurting. With only 6 and 10 runs, the comparison is directional, not statistically conclusive.

Batch results (16 runs). Poisoned file: quarantined 3/3; the words "500%", "admin mode", and "system prompt" appeared in 0 decks. Planted fake number: caught 3/3, every time fixed in draft 2. Clean runs: 10/10 passed on draft 1. No run shipped an unverified number. The checker is strict by design: it also rejects correct numbers the tools didn't compute (in the baseline test, 8 of the 9 numbers it couldn't verify turned out to be correct sums and shares). I chose false alarms over false confidence; section 8 covers the fix.

Data privacy. Client data is sent to the model provider (OpenAI, via Portkey when available). For real client work this needs an enterprise agreement with no training on inputs, or a firm-hosted model; the app keeps runs locally only.

8. Limits and next steps

What doesn't work yet

  • Not tested with a real user. The time savings above are estimates. A user-test kit (script, last month's deck, answer key, timing sheet) is in docs/user_test/, but the session has not been run.
  • It doesn't update your existing deck. It writes a fresh deck in its own template. Real teams want their firm's template and last month's slide order preserved.
  • The fact-checker is strict. It rejects correct derived numbers (sums of two segments, shares of growth) that the tools didn't compute, so the deck avoids them rather than risk being wrong.
  • Run-to-run variation. Slide wording and emphasis vary between runs; the numbers are always checked, but which story leads is not deterministic. With the old 200-fact cap the Footwear story was missed in 2 of 10 runs.
  • Narrow input. Two periods of tabular data with the same columns; no trends over many periods, no PDFs, no joins across files.
  • Synthetic data, small files. Tested on a fictional 32-row client; cost and quality on 5,000-row files are not measured.
  • Local prototype. Runs in server memory (a restart clears on-screen results), single global budget, no login.

With another month

  1. Template-aware refresh: open last month's .pptx, keep its layout and slide order, and update only numbers, charts, and titles whose story changed.
  2. A verifier for derived numbers: let the Storyliner propose a formula ("Apparel + Camping") that code recomputes, instead of banning derived figures.
  3. Pilot with my former team: run the user-test kit with two consultants, measure before/after time and errors, and iterate.
  4. Multi-period trends and data connectors (Excel workbooks, BI exports), plus hosting with per-user budgets and an enterprise model endpoint for client data.
